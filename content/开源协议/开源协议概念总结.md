看开源协议时，主要想弄清楚几件事：能怎么使用代码、要不要公开修改、有没有专利授权，以及能不能和其他协议放在一起。这里先记常见区别，具体项目还是要看对应版本的协议原文。

## 什么是开源协议

代码公开在网上，并不等于可以随便使用。开源协议是一份法律文件，说明代码可以怎么查看、修改和分发；没有协议时，不能仅凭“能看到源码”，就认为作者已经给出了这些授权。

可以先这样理解：作者仍然保留版权，只是通过协议**授予**一些使用权，同时可能要求保留声明、提供源码等。

## 核心维度说明

几种协议容易混在一起，可以先从下面这些方面对照：

1. **Copyleft 强度**：是否要求衍生作品也以相同协议开源
2. **商业友好度**：是否允许将代码用于商业产品或闭源分发
3. **专利授权**：是否明确授予专利权（防止贡献者后期发起专利诉讼）
4. **兼容性**：能否与其他协议的代码混合使用


> [!info] Copyleft 是什么
> Copyleft 大致是在版权许可中要求特定范围的衍生作品继续开放，而不是放弃版权。它的范围和触发条件要看具体协议，不能一概理解成“用了代码，整个项目就必须公开”。

## MIT 协议

**全称**：The MIT License

**一句话总结**：限制比较少，不过分发时要保留版权声明和协议文本。

### 关键条款

- ✅ 允许商用、闭源、修改、分发、私人使用
- ✅ 不提供任何担保（作者不承担代码出问题的责任）
- ⚠️ 分发时必须附带原版权声明和协议文本
- ❌ **不包含专利授权条款**（理论上作者可以后续就代码中的专利提起诉讼）

### 典型使用场景

MIT 在 npm 包、Rust crate 和小型开源库中都比较常见，条款也相对简短。

```text
MIT License

Copyright (c) 2025 张三

Permission is hereby granted, free of charge, to any person obtaining a copy...
```


> [!warning] 注意
> MIT 没有明确写出专利授权条款。如果需要明确的专利许可，可以进一步看 Apache 2.0 的相关规定。


---

## Apache 2.0 协议

**全称**：Apache License 2.0

**一句话总结**：也是宽松协议，但比 MIT 更明确地规定了专利授权、声明保留和商标使用边界。

### 关键条款

- ✅ 与 MIT 同样允许商用、闭源、修改、分发
- ✅ **明确授予专利权**：贡献者自动授予使用者相关专利许可
- ✅ **专利诉讼终止**：如果使用者对代码发起专利诉讼，协议自动终止
- ⚠️ 修改过的文件必须声明做了改动
- ⚠️ 保留 NOTICE 文件（如有）

### 与 MIT 的核心区别

| 维度        | MIT    | Apache 2.0 |
| ----------- | ------ | ---------- |
| 专利授权    | 无     | 明确授予   |
| 专利防御    | 无     | 诉讼即终止 |
| NOTICE 文件 | 不需要 | 需保留     |
| 修改声明    | 不强制 | 必须标注   |

Kubernetes、TensorFlow 等项目使用的就是 Apache 2.0。

---

## GPL 协议

**全称**：GNU General Public License

**一句话总结**：强 Copyleft，分发受其约束的衍生作品时，也需要按相应 GPL 条款提供源码。

### GPLv2 vs GPLv3

| 维度               | GPLv2     | GPLv3                 |
| ------------------ | --------- | --------------------- |
| 发布日期           | 1991      | 2007                  |
| 专利条款           | 无        | 有（类似 Apache 2.0） |
| 反 Tivo 化         | 无        | 有（禁止硬件锁死）    |
| 与 Apache 2.0 兼容 | ❌ 不兼容 | ✅ 兼容               |

"Tivo 化"是指硬件设备使用了 GPL 代码，但通过数字签名锁死硬件，阻止用户真正运行修改后的版本。GPLv3 明确禁止这种行为。

### 关键条款

- ✅ 允许商用、修改、分发
- ❌ 分发时必须公开源码（包括使用了 GPL 代码的衍生项目）
- ❌ 如果以二进制形式分发，必须同时提供对应源码或书面提供源码获取方式
- ⚠️ 网络服务（SaaS）不触发分发义务——这是 AGPL 要解决的问题


> [!important] GPL 的"传染性"
> 这里要区分内部使用和对外分发。只在内部运行 GPL 软件，通常不会因此要求公开内部工具或个人笔记；向外分发时，才需要按对应版本履行源码提供等义务。


### 典型使用场景

Linux 内核（GPLv2）、GCC、Bash、Git 等 GNU 项目。

---

## AGPL 协议

**全称**：GNU Affero General Public License

**一句话总结**：在 GPL 的基础上，补上修改版通过网络提供服务时的源码提供要求。

### 核心补充

GPL 的源码提供义务主要围绕**分发**展开，单纯让用户通过网络使用服务，不等于给了用户一份软件副本。AGPL 针对这个场景增加了要求：修改程序后，要让通过网络与它交互的用户有机会取得对应源码。它不是简单地把所有网络访问都改称“分发”。

```text
GPL:  修改代码 → 不对外分发 → 无需开源
AGPL: 修改代码 → 部署为网络服务 → 必须开源
```

### 典型使用场景

Grafana、MinIO 等项目曾使用或提供 AGPL 版本。数据库和基础设施项目的许可证可能变化，比如 MongoDB 后来改用 SSPL，判断具体版本时不能只看项目名字。

---

## LGPL 协议

**全称**：GNU Lesser General Public License

**一句话总结**：较弱的 Copyleft，满足相应条件时，闭源应用也能使用这个库。

### 核心思想

闭源应用可以在满足 LGPL 条件的情况下**动态链接**库；如果修改了库本身，分发时还需要提供对应修改。应用和库各自承担什么义务，要分开看。

```text
GPL:  闭源应用 <link> GPL库    → 应用必须开源 ❌
LGPL: 闭源应用 <link> LGPL库   → 应用可以闭源 ✅（但库的修改需开源）
```

### 典型使用场景

Qt（LGPL 版本）、GTK、glibc 等希望被广泛使用的底层库。

---

## BSD 协议

**全称**：Berkeley Software Distribution License

**一句话总结**：同样比较宽松，不过要区分 2-Clause 和 3-Clause，后者还有禁止借作者名义背书的条款。

### BSD 2-Clause vs BSD 3-Clause

| 条款         | BSD 2-Clause | BSD 3-Clause |
| ------------ | ------------ | ------------ |
| 保留版权声明 | ✅           | ✅           |
| 禁止背书条款 | ❌           | ✅           |
| 免责声明     | ✅           | ✅           |

“禁止背书条款”：未经许可，不能借原作者的名义宣传产品。例如，只有李四确实认可产品时，才能说“李四认可这款产品”。

### 典型使用场景

FreeBSD 系统、Go 语言部分组件、Nginx。

```text
BSD 2-Clause ≈ MIT（功能几乎等价）
BSD 3-Clause ≈ MIT + 禁止背书
```

---

## MPL 2.0 协议

**全称**：Mozilla Public License 2.0

**一句话总结**：文件级 Copyleft，分发时需要开放受其约束文件的修改，但可以和其他闭源文件放在同一个项目中。

### 核心特点

- ✅ 允许商用、闭源项目中使用（只需开源 MPL 代码文件本身）
- ✅ 与 Apache 2.0、GPLv2、LGPLv2.1 兼容
- ✅ 包含专利授权条款
- ⚠️ 修改过的 MPL 文件必须开源

```text
GPL copyleft 范围：整个项目
MPL copyleft 范围：单个文件
```

### 典型使用场景

Firefox、Thunderbird、Rust 编译器（部分组件）。

---

## Unlicense / CC0

**一句话总结**：放弃一切权利，进入公共领域。

- **Unlicense**：适用于代码，完全放弃版权和相关权利
- **CC0（Creative Commons Zero）**：适用于文档、图片、数据等非代码内容


> [!warning] 法律风险
> 各个法域对放弃版权的规定不一样，比如德国涉及作者人格权的限制。因此不能只看“公共领域”几个字，就认为所有权利都已经没有限制；不确定时还是要核对协议和适用法律。

| MIT          | ✅   | ✅             | ❌       | 无             | React, jQuery          |

| BSD 3-Clause | ✅   | ✅             | ❌       | 无             | Go                     |

## 协议兼容性

不同协议的代码不一定都能直接混用。下面只作简化速记，具体还得看版本、组合方式和实际条款：

```text
兼容方向：宽松 → 严格

MIT/Apache 2.0/BSD  →  可以合并到 GPL 项目中
GPL 代码             →  不能合并到 MIT 项目中

Apache 2.0  ←→  GPLv3 兼容
Apache 2.0  ←→  GPLv2 不兼容（专利条款冲突）
```


> [!important] 兼容性需要分情况看
> 不能只按“宽松”或“严格”排一个顺序，就判断两份代码能不能组合。比如 MIT 代码通常可以放进 GPL 项目，但 GPL 代码的再分发不能因此去掉原有义务。还要继续看 GPL 的版本和实际使用方式。

## 选型建议

| 场景                                   | 推荐协议        |
| -------------------------------------- | --------------- |
| 个人小工具、简单库，不在乎别人怎么用   | MIT             |
| 需要专利保护，公司项目，不想担责       | Apache 2.0      |
| 希望代码修改必须回馈社区               | GPLv3           |
| 基础设施/数据库，防止大公司白嫖        | AGPLv3          |
| 开发库，希望被广泛使用（包括商用软件） | LGPL 或 MPL 2.0 |
| 完全不 care，放弃一切权利              | Unlicense / CC0 |


> [!info] 选择时先看用途
> MIT 和 Apache 2.0 都是常见的宽松协议，可以从用途、专利需求和依赖兼容性开始选。双协议授权则要先确认自己有权授权全部相关代码，不能把别人的贡献和依赖也当成可以随意换协议。

## GPL 系列与 MPL 深度对比

### 核心差异一览


> [!info] 关于"GPL（通用）"
> "GPL"泛指 GPL 协议的共性特征，不区分版本。具体到专利授权、反 Tivo 化、兼容性等细节，需看 GPLv2 或 GPLv3 列。


| 维度               | GPL（通用） | GPLv2    | GPLv3    | LGPL           | MPL 2.0      |
| ------------------ | ----------- | -------- | -------- | -------------- | ------------ |
| Copyleft 范围      | 整个项目    | 整个项目 | 整个项目 | 仅库本身       | 单个文件     |
| 闭源衍生           | ❌          | ❌       | ❌       | ✅（动态链接） | ✅（新文件） |
| 专利授权           | 视版本而定  | ❌       | ✅       | ❌             | ✅           |
| 反 Tivo 化         | 视版本而定  | ❌       | ✅       | ❌             | ❌           |
| 与 Apache 2.0 兼容 | 视版本而定  | ❌       | ✅       | ❌             | ✅           |
| 分发时必须开源     | ✅          | ✅       | ✅       | ✅（仅库修改） | ✅（仅文件） |

### 三组关键区别

**GPLv2 vs GPLv3**：GPLv3 增加了专利授权（防止专利诉讼）、反 Tivo 化（禁止硬件锁死阻止用户运行修改后的代码）、以及与 Apache 2.0 的兼容性。Linux 内核坚持使用 GPLv2，因为 Linus Torvalds 反对反 Tivo 化条款。

**GPL vs LGPL**：LGPL 允许闭源应用在满足条件时**动态链接**库，不必因此把整个应用改成 LGPL。但库本身的修改仍有对应义务。静态链接也不等于一定要公开整个应用，还要看具体版本对重新链接等条件的要求。

**GPL vs MPL**：两者的 Copyleft 范围不同。GPL 更关注受其约束的整体衍生作品，MPL 则以**单个文件**为边界。分发时，修改过的 MPL 文件需要提供对应源码，独立新增的其他文件可以采用不同协议。

### 代表性软件

#### GPLv2

| 项目       | 简介                                          |
| ---------- | --------------------------------------------- |
| Linux 内核 | 操作系统内核，坚持 GPLv2 拒绝升级到 GPLv3     |
| Git        | 分布式版本控制系统                            |
| BusyBox    | 嵌入式 Linux 的"瑞士军刀"，集成大量 Unix 工具 |

#### GPLv3

| 项目 | 简介                                              |
| ---- | ------------------------------------------------- |
| GCC  | GNU 编译器套件，支持 C/C++/Rust 等多语言          |
| Bash | GNU 命令行 Shell，大多数 Linux 发行版的默认 Shell |
| GDB  | GNU 调试器                                        |

#### LGPL

| 项目  | 简介                                             |
| ----- | ------------------------------------------------ |
| glibc | GNU C 标准库，几乎所有 Linux 程序都依赖它        |
| GTK   | GUI 工具包，GNOME 桌面环境的基础                 |
| Qt    | 跨平台 GUI 框架（LGPL 版本），KDE 桌面环境的基础 |


> [!info] 为什么 glibc 用 LGPL 而非 GPL
> glibc 是系统级基础库，如果采用 GPL，所有链接它的程序都必须开源，这会严重阻碍 Linux 生态发展。LGPL 让闭源商业软件也能在 Linux 上运行。


#### MPL 2.0

| 项目        | 简介                     |
| ----------- | ------------------------ |
| Firefox     | Mozilla 浏览器           |
| Thunderbird | Mozilla 邮件客户端       |
| LibreOffice | 开源办公套件（部分组件） |

### 选型速查

```text
想让修改必须回馈社区？
├── 是 → 整个项目都要开源 → GPLv3
│        只要求库本身开源 → LGPL
│        只要求单个文件开源 → MPL 2.0
└── 需要防止硬件锁死？ → GPLv3
```


> [!warning] GPLv2 与 GPLv3 不兼容
> GPLv2 和 GPLv3 之间**不兼容**——不能将 GPLv2 only 的代码与 GPLv3 代码合并。但许多项目声明 "GPLv2 or later"，此时可以选择以 GPLv3 使用。Linux 内核是 "GPLv2 only"，无法与 GPLv3 代码混合。
