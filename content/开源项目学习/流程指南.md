学习开源项目，可以先选一个合适的项目，跑通功能，再带着问题读源码，最后试着写个最小原型或者参与贡献。这里先记一个大致顺序，实际做了哪些再另外记录。

## 阶段一：选对项目

### 筛选条件

可以先用 GitHub 高级搜索缩小范围。刚开始找规模适中的项目就好，不一定越热门越合适；下面的语言占位符换成准备学习的语言：

```bash
stars:500..5000  language:你的语言  pushed:>2025-01-01
```

### 快速检查三个指标

- 有没有 `CONTRIBUTING.md`，先看看项目的贡献流程。
- Issues 里有没有 `good first issue`，找找适合入门的任务。
- 最近一周有没有 commit，再结合项目的更新节奏判断是否活跃。

### 本地跑通

```bash
git clone <repo-url> && 按照 README 把项目跑起来
```

先照文档试着跑起来。如果环境问题太多，可以记下卡在哪里，再考虑换一个更容易上手的项目，不必一开始就把时间全花在配置环境上。


> [!info] 具体推荐
> 按语言挑选入门项目：
> 
> - **Go**：`fzf`（CLI 工具，模糊搜索）
> - **Python**：`rich`（终端美化，ANSI 转义码）
> - **JS**：`htmx`（前端库，增量 HTML）
> - **Rust**：`bat`（cat 替代品，代码量适中）

## 阶段二：先成为用户

### 熟悉全部功能

先把项目的 CLI 子命令或 API 方法列出来，从常用功能开始试，记一下输入和输出，再慢慢补全。

### 猜实现并验证

先挑 3 个感兴趣的功能，记下对实现方式的猜测。

例如用 rich 打印彩色表格，先猜它怎样处理 ANSI 转义码，再去源码中验证。

### 用调试器跟踪调用栈

按项目使用的语言选择调试器：

```bash
# Python
python -m pdb script.py

# Go
dlv debug main.go

# Node.js
node --inspect-brk script.js
```

发起一个请求或者执行一条命令，打断点单步跟进去，看调用经过了哪些函数，会比只看目录更容易理解。

## 阶段三：带着问题读源码

读源码不急着从 `main()` 一路往下看，先按以下三圈递进。

### 第 1 圈：读懂接口层

找项目的 public API 或 entry point：

| 语言   | 查找方式                              |
| ------ | ------------------------------------- |
| Python | `__init__.py` 里 `__all__` 列出的符号 |
| Go     | 包根目录导出的函数（首字母大写）      |
| Rust   | `lib.rs` 里的 `pub mod` + `pub fn`    |
| JS/TS  | `index.ts` 中的 `export` 语句         |

这一圈先看函数签名和 docstring，弄清楚接口要什么、返回什么，具体实现可以先不展开。

### 第 2 圈：追踪功能的完整链路

选一个前面猜过实现的功能，按“从入口到细节”的顺序往下追：

- **顶层**：用户调用的那个函数
- **中层**：它调了谁？数据在哪些对象间流转？
- **底层**：最终落到什么系统调用或网络请求？

用纸笔或 Excalidraw 画一张调用关系草稿，只画已经追踪过的地方。

### 第 3 圈：读最早期的 commit

```bash
git log --reverse --oneline | head -20
git show <first_commit_hash>
```

有些项目早期版本很简单，先看最初怎么搭起来，也能减少“代码这么多，肯定看不懂”的压力。

### 实操技巧

- 用 `rg "函数名" --type py`（或对应语言）快速跳转定义处
- 随手在源码旁记下理解，用 `# 注释` 标记（不要提交）
- 遇到看不懂的，Google 搜 `项目名 + 函数/类名 + blog`，大概率有人写过分析

## 阶段四：写最小原型

### 剥离核心模块

只复制一个核心模块到新目录：

```bash
cp -r 原项目/src/core  my-clone/
```

这里是做最小原型，可以先尽量隔离外部依赖，只留下要理解的那个模块。

### 用自己的方式重写

- 变量名按习惯改
- 为了看清核心逻辑，可以在这个独立原型里暂时去掉边界处理和性能优化，但别把简化版当成正式实现。
- 每改一小段，比如 20 行左右，就跑一次测试，看看有没有把行为改坏。

### 与原版对比

```bash
diff -r 你的版本 原版
```

把最小原型和原版对比，重点看那些看似“多余的代码”解决了什么问题。

## 阶段五：参与贡献

参与贡献也可以慢慢来，不必第一次就做新功能。先从改文档、补测试开始，再尝试修 bug。

### Level 0：修改文档或注释（第 1 次 PR）

- 找 README 里的拼写错误
- 补一个入参说明
- 翻译一段文档

目的：熟悉 fork → branch → PR → review 全流程。

### Level 1：补测试（第 2~3 次 PR）

- 在 CI 面板找 coverage report
- 挑一个 coverage 低于 80% 的文件
- 写 2~3 个单元测试

这里主要是检查自己有没有理解函数接收什么、返回什么，以及特殊输入会怎样。

### Level 2：修 bug（第 4~5 次 PR）

- 挑 `good first issue` 标签的 bug
- 先在本地复现，打断点定位，写修复，加回归测试
- Push 前按项目的贡献要求整理 commit；需要用 `git rebase -i` 时，先确认不会误改共享历史。

### Level 3：实现小型 feature

- 先开 issue 描述提案，等 maintainer 点头
- 参考项目已有的类似 feature 代码，模仿其模式
- PR 描述写清楚：What / Why / How


> [!warning] 注意
> 这个阶段不用追求第一次提交就完全合适，可以从 review 反馈里慢慢理解项目的写法和设计习惯。

## 每日节奏建议

| 时间段        | 做什么                            | 目的             |
| ------------- | --------------------------------- | ---------------- |
| 前 30 分钟    | `git pull && 浏览新 commit/issue` | 保持对项目的感知 |
| 核心 1.5 小时 | 按阶段三/四深读或写代码           | 真正的学习       |
| 最后 20 分钟  | 把今天搞懂的写 3~5 句话笔记       | 积累会复利       |

---

## 常见坑及对策

| 踩坑                          | 对策                                                     |
| ----------------------------- | -------------------------------------------------------- |
| 看了 30 分钟不知所云，想放弃  | 换个更小的文件重来；或者跳到阶段四先写                   |
| 遇到不认识的语法或模式        | 立刻查，但只查这一个点，别发散；查到后原地写一行注释标记 |
| 总觉得"自己写的太烂不敢发 PR" | 先从改 typo 开始，不必把第一个 PR 想得太难            |
| 项目太大，不知道从哪开始      | 反复回到阶段三第 2 圈，"追踪一个功能"是万能入口          |
| PR 提交后被要求大改           | 正常现象，耐心逐条回应 review 意见即可                   |

## 常用命令速查

```bash
# 查看项目最早的 10 个 commit
git log --reverse --oneline | head -10

# 搜索某个函数在代码中的所有引用
rg "function_name" --type py

# 查看某个文件的所有 commit 历史
git log -p -- path/to/file

# 交互式 rebase，合并 commit
git rebase -i HEAD~3

# 拉取上游更新并变基
git pull --rebase upstream main
```
